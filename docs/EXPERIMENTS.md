# Експерименти (Лаб №3, завдання 2)

Одна бізнес-функція, `PublishRelease` (опублікувати перевірену збірку `cosmos.db`), реалізована двома способами над спільною сагою «резерв → switch `version.json` → позначка → (аудит)»:

- **Класичний** (`?mode=classic`): синхронні виклики, відповідь клієнту після всіх кроків, аудит у `telemetry` обов'язковий. Збій кроку відкочує попередні.
- **Подієвий** (`?mode=eda`): запит повертає `202`, воркер виконує ті самі кроки з повторами й backoff, результат розходиться подіями (outbox → RabbitMQ → `telemetry`, gateway). Збій кроку теж відкочує.

## Методика

`tools/bench` на запущеній платформі (Docker Compose, один хост) публікує релізи послідовно, по N=50 на режим і сценарій. Одна й та сама перевірена збірка використовується щоразу: після кожного релізу бенч знімає резерв (`DELETE /v1/builds/{id}/reserve`). Метрики: p50 і p95 (nearest-rank), частка помилок. Для подієвого режиму «Відповідь» це час до `202`, «Завершення» час до `published`/`failed` (опитування кожні 50 мс). Збої вмикаються так: `docker compose stop telemetry|rabbitmq`, затримка `catalog` через `/debug/fault`.

| Сценарій | Що перевіряє |
|---|---|
| S1 | норма |
| S2 | `telemetry` зупинено |
| S3 | `catalog` +2 с затримки на кожен запит |
| S4 | брокер зупинено під час публікації (outbox тримає подію) |
| S5 | та сама подія доставлена двічі (аудит не дублюється) |
| S6 | `telemetry` піднявся і дочитав чергу |

Відтворення: `go run ./tools/bench` (≈15 хв), покроково в `docs/MANUAL_M4_M5.md`.

## Аналіз

**Затримки.**
- У нормі (S1) обидва режими завершуються за ~60 мс, але клієнт подієвого режиму отримує відповідь за ~5 мс (у ~10 разів швидше): йому не потрібно чекати кроки. Завершення подієвого режиму не довше за класичне, бо воркер прокидається одразу після запиту (`Wake`), а не за таймером.
- Повільний `catalog` (S3, +2 с на запит) показує головну різницю. Класичний режим робить два виклики `catalog`, тож клієнт чекає **~4,05 с** (сума затримок). Подієвий відповідає за ~5 мс, а реліз завершується за ті самі ~4,1 с у фоні. Повний час не зменшився, але клієнт не блокується, і HTTP-з'єднання не стоїть відкритим.

**Відновлення після збоїв.**
- `telemetry` зупинено (S2): класичний режим **провалив 100 %** публікацій, бо аудит обов'язковий, кожна закінчилась відкатом (`502`, `version.json` і резерв повернено, перевірено в «Релізах» і трейсом `classic-fail`). Швидка відповідь помилки (~50 мс) пояснюється circuit breaker: після 3 невдач клієнт `release` перестає чекати timeout. Подієвий режим **не втратив жодної** публікації (50/50), бо аудит не в критичному шляху.
- Брокер зупинено (S4): класичний режим його не використовує, тож не помітив. Подієвий теж опублікував усі 50 релізів, а події чекали в outbox; після запуску брокера всі 50 дійшли до аудиту за ~6 с. Втрат немає, порядок збережено.
- `telemetry` повернувся (S6): усі 50 подій дочитано з черги за ~5 с після запуску.
- Дублікат (S5): повторна доставка не створює повторного запису: inbox дедуплікує за `event.id` (50 подій, по 2 доставки, 50 рядків).

**Складність розробки.** Класичний режим має ~32 рядки власного коду і один додатковий компонент (клієнт аудиту). Подієвий потребує ~770 рядків і сім компонентів (outbox, relay, inbox, брокер, воркер, споживач, SSE), бо додає нові види збоїв: недоставлена подія, дублікат, зупинка посередині саги, воркер, що завис. Спільна сага (~290 рядків) однакова, бо компенсації потрібні в обох режимах. Більшу частину подієвого коду складає багаторазова інфраструктура (`outbox`, `mq`, `inbox`), яка окупається, коли подій і споживачів стає більше (research, нові слухачі `release.published`).

**Висновок.** Для критичного синхронного сценарію, де клієнт має знати результат одразу, а залежності надійні, достатньо класичного режиму. Коли побічні дії (аудит, сповіщення, наступні задачі) не мають блокувати основний результат або залежності ненадійні чи повільні, подієвий режим дає відповідь за мілісекунди, переживає збої залежностей без втрат і не дублює дії, ціною значно більшої складності та кінцевої узгодженості (аудит з'являється з затримкою). Гібрид, обраний у платформі (сага в `release` + хореографія для побічних ефектів), поєднує обидва підходи.

**Обмеження.** Усе на одному хості, збірка одна й та сама, затримки мережі між контейнерами мінімальні; N=50 достатньо для p50, а p95 по 50 точках грубий (48-ма за зростанням). S4/S6 для класичного режиму не мають власних рядків: S4 класичний не залежить від брокера (рядок у таблиці), S6 повторює S2 для зупиненого `telemetry`.
